# 設計メモ (調べて分かった落とし穴と、その出所)

独立レビューで、実測または原典 (公式ドキュメントとクレートのソース) で確かめた事実をまとめる。
**ここは事実の置き場で、判断は docs/decisions.md に書く。** 実装前に一度通して読むこと。
版の数字は調査した時点のもの。変えるなら、理由を判断ログに残す。

## 端末と TUI

- Claude Code の Bash ツールも PowerShell ツールも、標準入力、標準出力、標準エラーはすべてリダイレクトされていて、端末ではない
  (via: 検証者が Bash では `[ -t 0 ]` `[ -t 1 ]` `[ -t 2 ]`、PowerShell では `[Console]::IsInputRedirected` などで確認)
- crossterm 0.29.0 の Windows 実装は、`enable_raw_mode` で標準入力ではなくコンソールの入力バッファ (`CONIN$`) を直接開く
  (via: crossterm 0.29.0 の `src/terminal/sys/windows.rs` の 31 行目付近と、crossterm_winapi 0.9.1 の `src/handle.rs` の 143 行目付近)。標準入力をパイプにしても、親のコンソールを raw にしてしまうことがある。判定は標準入力と標準出力の両方が端末のときだけ起動にする (D-023)
- Rust の標準ライブラリの `IsTerminal` は、`GetConsoleMode` が失敗したとき、mintty 系 (msys や cygwin の pty) の名前で端末かを判定する
  (via: Rust 標準ライブラリの `library/std/src/sys/io/is_terminal/windows.rs`)
- Windows の crossterm は、1 回の打鍵で Press と Release の両方のイベントを流す (via: `src/event/sys/windows/parse.rs` の 285 行目付近)。`KeyEventKind::Press` だけを処理しないと、トグルやカーソル移動が二重に実行される
- raw モードでは `ENABLE_PROCESSED_INPUT` が落ちるので、Ctrl+C はシグナルにならず、`KeyEvent` (Char('c') と CONTROL) で届く (via: `src/terminal/sys/windows.rs` の 18 行目付近)。自前で終了に割り当てないと、TUI を終了できない
- ratatui 0.30.2 の `ratatui::init()` は panic フックを入れて端末を復元する。`Terminal::new` は入れない。crossterm は ratatui の再エクスポート (`ratatui::crossterm`) を使い、別に足して版がずれるのを避ける
- ratatui 0.30.2 (ratatui-core 0.1.2) の差分描画は、VS16 (U+FE0F) を含まない幅 2 の文字 (CJK など) のセルを処理すると、変化の有無にかかわらず次のセルを飛ばす
  (via: ratatui-core 0.1.2 の `src/buffer/diff.rs` の 152 行目 (変わっていないセル) と 173 行目 (変わったセル) の `self.pos += cell_width.saturating_sub(1)` を読んだ。
  VS16 つきの絵文字が変わったときだけは 162 から 171 行目で次のセルも見る)。
  ポップアップの左端のセルが、下に残る全角文字の右半分に当たる行では、`Clear` と枠を描いても `╔` `║` `╚` が端末に送られない。
  Windows Terminal でヘルプと実行の確認の左枠が一部の行で消えた (2026-10-08、利用者の画面で確認)。描く前に左隣のセルが全角なら消す (D-046)。
  右端は幅 1 の文字で全角の左半分を上書きする形になり、端末が右半分を消すので崩れない
- TUI は「状態」「更新 (`update(&mut self, ev) -> Effect`)」「描画」に分け、更新を純関数にする。描画は `TestBackend` のバッファを標準出力にも出すと、評価者が会話で確認できる。`Release` イベントが何も起こさないこと、Ctrl+C が終了になること、リサイズで再描画されることを、テストに入れる

## 設定ファイル

- `dirs` 7.0.0 (dirs-sys 0.5.0) は、Windows では `SHGetKnownFolderPath` で既知のフォルダを引く。環境変数 (`APPDATA` や `USERPROFILE`) は、Unix 側の `HOME` と `XDG_*` しか読まない
  (via: dirs-sys 0.5.0 の `src/lib.rs` の 153 行目付近)。環境変数で `APPDATA` を一時ディレクトリに向けても、実際のユーザー設定の場所が返る。**既定のパス解決は 1 つの関数に隔離して、差し替えられるようにする。** テストでは `target/` を返す関数を渡し、実の既定関数が呼ばれたら panic するトリップワイヤを置く (D-010)
- serde 経由の `toml` はコメントを保持しない。TUI の保存で人間の手書きの設定を壊さないよう、`toml_edit` で差分編集する (D-018)
- 設定は、指定されたものが既定を置き換える形にしない。AI が呼ぶツールで、AI 自身が緩い設定を指定できると、人間の deny を回避できる (D-018)
- Windows のパスを字面で判定するときの落とし穴 (D-075、撮影の保存先と `capture.save_dirs`): (1) ドライブ相対の `D:x.png` は `cwd.join` しても絶対にならない (`Path::is_absolute` は偽で、そのドライブの作業ディレクトリは OS 側が持つ)。フォルダの包含は「絶対でなければ外れ」にして安全側に倒す。(2) `:` を含むファイル名は代替データストリームで、`C:\docs\report.docx:a.png` は拡張子が png に見えるのに既存の `report.docx` に書き込める (NTFS の名前付きストリームの仕様。ai-cu では書いて確かめず、形の判定でドライブの `:` より後ろの `:` を断る)。(3) `\\?\` と `\\.\` で始まるパスは OS が `.` と `..` を畳まないので、字面の正規化と比べ方がずれる。常に断る。拡張子は字面で、既存ファイル (PNG の署名) は検証の時と書く直前の 2 か所で確かめる。書く直前 (`PngFileWriter`) は確認と書き込みを同じハンドルで行うので、確認の後に差し替えられても潰さない
  (via: src/image.rs の `save_path_shape_accepts_png_only`、`normalize_save_path_folds_dots_against_cwd`、`png_file_writer_refuses_non_png_target_and_keeps_its_bytes`)

## Windows の入力

- `GetLastInputInfo` の時刻 (`dwTime`) は、人の入力だけでなく `SendInput` で入れたイベントでも更新される。しかも単調とは限らず、`SendInput` は自分の tick を持ち込むので前のイベントより小さい値になりうる
  (via: microsoft-learn の GetLastInputInfo の Remarks「an event raised by SendInput, which supplies its own tick count」を読んだ。単調とは限らないことは実測はしていない)。
  `SendInput` で更新されることは、この PC でキーとマウスの両方を確かめた。キー: 予告の間 (D-093) にフィクスチャへ `SendInput` で Shift を押して離すと、予告の終わりに読んだ無操作は 797 ms で、送り終えてから実行器が返るまでの 792 ms とほぼ等しかった (1 回の計測。差は `GetTickCount` の刻みの範囲)。マウス: 予告の間のカーソルのずれの判定を一時的に外すと、`SendInput` の移動だけで予告の終わりの無操作の判定が 10 `lead_input` を返した (D-095)
  (via: `python scripts/verify.py --ignored --continue --jobs 4` の `target/verify/ignored.log` の `FIXTURE lead key exit=10 returned_ms=1575 sent_to_return_ms=792 idle_ms=797 hidden_in_ms=28`。マウスは対照で `cargo test --test fixture_real fixture_real_lead_stops_on_injected_mouse_move -- --ignored --nocapture --test-threads=1 --exact` が `FIXTURE lead mouse exit=10 returned_ms=1541` を出して落ちた。2026-10-29)。
  `shot` の無操作の判定 (D-049) では、`run` の直後も「操作中」になる。`GetTickCount` との差は `wrapping_sub` で取り、「いま」より先に見える値 (余裕 60 秒) は 0 (直前の入力) に倒す。
  見るのは呼び出したセッションの入力だけで、RDP など別のセッションの操作は数えない (同じ Remarks)
- 入力デスクトップが Winlogon に切り替わった後 (資格情報の画面など) は、`GetCursorPos` は `ERROR_ACCESS_DENIED` (5) で失敗し、`GetForegroundWindow` は null を返す。ロックの直後の幕の間は、入力デスクトップは `Default` のままで、前面は LockApp.exe (手順 20。2026-10-15 に、ロックの後に人が触れていない幕の間の `run` の `error.detail.input_desktop` が `Default` だった)。幕の間に `GetCursorPos` が通ることと、資格情報の画面で 5 になることは推定 (2026-10-09 の測定は、ロックからの経過や画面の状態を記録していない)。実行器は操作に入る前にセッションのロックと入力デスクトップを判定し、入力、focus、撮影を含む操作列は、ロック中は何も送らずに 14 (`desktop_unavailable`、`reason: locked` (WTS で読めたとき)) で止まる。WTS が読めなければ、Winlogon に切り替わった後は `other_desktop`、幕の間は判定を素通りし、入力は前面のガード (7) が、focus は 11 が断る。撮影 (`shot` と `screenshot` のステップ) は前面のガードを通らないので、この場合はロック画面を撮って成功として返す (落とし穴。AI が誤った絵を見る) (撮影を付けない close、wait、wait_for だけの操作列は判定せず、5 ならマウスの監視なしで走る。D-066、D-067、D-068)。判定が漏れても、停止要因の確認で呼ぶ `GetCursorPos` の 5 を `BackendError::DesktopUnavailable` として 14 に写す (D-066。それまでは 8 の os_error だった)。途中のステップでは、撮影と focus の直前に同じ判定を通し、ロックとセーバーなら 14、判定が読めなければ 8。入力のステップは、入力デスクトップが切り替わった後 (資格情報の画面など) なら 14、ロックの幕の間は前面のガード (7) が断る。画面の待ち (`wait_stable`、`wait_change`) と `screenshot` の `settle` は撮影の仲間で判定する側に入り、操作列の最初に加えて撮るたびに同じ判定を通す (待つ間にロックされれば次の撮影で 14)。ただし WTS が読めない幕の間は、`screenshot` と同じく判定を素通りし、ロック画面を撮り続けて「落ち着いた」と返しうる (D-081)
  (via: 2026-10-09 に利用者が画面をロックした状態で `cargo test -- --ignored --nocapture --test-threads=1` を走らせ、入力を送る 9 件が `GetCursorPos が失敗 (GetLastError=5)` で止まり、`ai-cu windows` の `foreground` が null だった。UIA のテストはロック中でも通った)。再試行では直らないので、14 の hint で人に解除を頼むよう伝える

- 対話の窓口 (Winsta0) には `Default`、`ScreenSaver`、`Winlogon` の 3 つのデスクトップがある。保護付きのセーバーは `ScreenSaver` に入力デスクトップを切り替える。ロックの幕 (LockApp.exe) の間は `Default` のまま (2026-10-15 に実測。via: ロック中に `target/release/ai-cu.exe run target/manual-check/lock_click.json` の出力の `error.detail.input_desktop`)、資格情報の画面で `Winlogon` (推定。値は直接読んでいない)。Ctrl+Alt+Del と UAC は `Winlogon`。保護なしのセーバーは `Default` の上で動くので名前では分からず、`SystemParametersInfoW(SPI_GETSCREENSAVERRUNNING)` で見る (via: Microsoft Learn の「Desktops」と `SystemParametersInfoW`)。D-066 の判定 (D-067 で補った) の順は、セーバー → WTS のロック → 名前。セーバー動作中なら `ScreenSaver`、ロックと読めたら `locked` (入力デスクトップを開けなくても 8 にしない)、そうでなければ `OpenInputDesktop` + `GetUserObjectInformationW(UOI_NAME)` の名前が `Default` かで分け、開けない (5) か別の名前なら別のデスクトップ。5 以外で開けないときは 8 (判定が読めないのを「ロック」と決めつけない)
- セッションのロックは `WTSQuerySessionInformationW(WTSSessionInfoEx)` の `WTSINFOEX_LEVEL1_W.SessionFlags` で読む (`WTS_SESSIONSTATE_LOCK` ならロック。Windows 7 / Server 2008 R2 は LOCK と UNLOCK の値が逆になる既知の不具合があり、対処しない。読めなければ非ロックとして名前の判定に任せる。D-067) (via: Microsoft Learn の「WTSINFOEX_LEVEL1_W」)。ロックとセーバーは別の経路で、PC の設定によって片方だけが起きる (セーバーだけ、ロックだけ、ロック付きのセーバー)。だからセーバーの判定だけでもロックの判定だけでも足りない
- `GetAsyncKeyState` は、呼んだ側のデスクトップが active でないとき、UIPI で前面のスレッドに届かないとき、前面のスレッドが別のプロセスで、そのデスクトップへの `DESKTOP_HOOKCONTROL` か `DESKTOP_JOURNALRECORD` の権限が無いときに 0 を返す (via: Microsoft Learn の `GetAsyncKeyState`)。押されたままのキーの判定 (keys_held) は、見落とす向きには倒れても誤検出の向きには倒れない。マウスのボタンは物理のボタンの状態を返す (左右の入れ替えは反映しない)
- キーボード入力は前面のウィンドウに届き、マウス入力は座標の下のウィンドウに届く。したがって、マウスのテストは前面でなくても成立するが、キーのテストは前面の確認が必須
- `SetForegroundWindow` で前面にできる条件は、前面ロックのタイムアウトが切れた、呼び出したプロセスが前面プロセスである、前面プロセスに起動された、前面のウィンドウが無い、最後の入力イベントを受けた、デバッグ中、のいずれか。「ユーザーが別のウィンドウを使っている間は、強制的に前面にできない。代わりにタスクバーのボタンが点滅する」
  (via: Microsoft Learn の `SetForegroundWindow`)。この PC のタイムアウトは非常に大きい (CLAUDE.local.md)。対応は D-020
- 前面ロックを実機で測った (2026-10-09、試用のプロジェクトのセッションが `target/manual-check/verify_focus.py` を、利用者の GO の後に各ケース 1 回): 端末 (Zed.exe) が前面なら、その子プロセスからの `SetForegroundWindow` は 1 を返してメモ帳が前面になった。Chrome が前面なら 0 を返して前面は変わらなかった (`GetLastError` は 0)。Chrome が前面でも、最小化したメモ帳を `ShowWindow(SW_RESTORE)` で復元した直後の `SetForegroundWindow` は 1 を返して前面になった。復元は前面ロックの境界をすり抜ける (理由は未確認) ので、`focus` 操作は復元をしない (D-050)。Windows Terminal (pwsh の孫プロセス) から起動した ai-cu でも、端末が前面なら隠れたメモ帳を前面にできた (2026-10-09、利用者が手動確認の手順 15 を実施)。OS が断ったとき (ブラウザが前面) のタスクバーのボタンの点滅は、その観察では見られなかった (仕様には「点滅する」とあるが、1 回の観察では起きなかった)
- `EnumWindows` の列挙の順序は、Microsoft Learn には明記が無い (実装上は Z 順で、`windows` と `focus` の「前面に近いものから」と、撮影の機密のウィンドウの判定の `stack_windows` (D-077。順が違うと奥の窓を覆いとして引き、漏れる向きに倒れる) はそれに依存している)。保証が要るなら `GetTopWindow` と `GetWindow(GW_HWNDNEXT)` に替える
- `EnumWindows` は見えない窓も列挙する (Microsoft Learn「Enumerates all top-level windows」)。タスクトレイに隠れるアプリ (利用者のアプリ) は、主ウィンドウを隠している間も見えないトップレベルの窓を持ち、その持ち主として数えられた (via: 2026-10-22 の手動確認の手順 22。`target/release/ai-cu.exe windows` の `hidden_allowed` を、トレイから出す前後で比べた)。別の仮想デスクトップの窓は cloaked で、`IsWindowVisible` は真のまま、一覧 (`top_windows`) からは外れる。`windows` の `hidden_allowed` はこれらを持ち主の名前で拾う (D-074)。テストのプロセスはフィクスチャのほかに既定の IME の窓 (見えないトップレベル) を持ち、そのクラスは `MSCTFIME UI` と `IME` だった (3 つの見えない窓のうちフィクスチャ以外。この机の見えないトップレベルの窓は全部で 503 あった) ので、pid だけでは隠したフィクスチャを撃てず、hwnd で確かめる。`windows --include-hidden` (D-099) はこの 2 つのクラスを雑音として除く
  (via: `python scripts/verify.py --ignored` の `target/verify/` のログの `FIXTURE hidden_top_windows total=503 own=3 own_classes=["MSCTFIME UI", "IME"]`。HEAD 06c4f29、2026-11-03)

## 実装して分かったこと (2026-10-08、TUI からの実行)

- 実行器と装置層は標準出力にも標準エラーにも書かないので、ratatui の代替画面を保ったまま同期で `Executor` を呼べる。`ratatui::restore()` と `try_init()` を往復しない (ratatui 0.30.2 は `try_init` ごとに panic フックを積む)

## MCP サーバーモード (2026-10-09、D-055)

- MCP の現行版は 2026-07-28 で、`initialize` の握手を廃した stateless 方式。各リクエストが `params._meta` に `io.modelcontextprotocol/protocolVersion` (必須) と `io.modelcontextprotocol/clientCapabilities` (必須) を載せ、欠けていれば -32602、版が合わなければ -32022 (`data` に `supported` と `requested`)。サーバーは `server/discover` に必ず応え (`supportedVersions`、`capabilities`、`instructions`、`ttlMs`、`cacheScope`)、すべての結果に `resultType: "complete"` を、`server/discover` と `tools/list` の結果に `ttlMs` (0 以上) と `cacheScope` を付ける (MUST)。`ping` は廃止。旧版 (2025-11-25 以前) は `initialize` → `notifications/initialized` の握手で、サーバーは要求された版を知っていればその版、知らなければ自分の最新を返す。バッチ (配列) を許すのは 2025-03-26 だけ (2025-06-18 で削除)
  (via: modelcontextprotocol.io の 2026-07-28 の versioning、basic/index、transports/stdio、server/discover、server/tools、server/utilities/caching、basic/utilities/cancellation と、2025-06-18 の lifecycle、2025-11-25 と 2026-07-28 の changelog を読んだ)

## 検証と運用

- `cargo test` の `test result:` の行は、ライブラリ、バイナリ、各結合テスト、ドキュメントテストごとに出る。`grep -E "test result|FAILED|panicked"` で全行を出す。ビルドが失敗してログが空のときは、grep も空になり、「すべて成功」が空の集合で真になる。件数が 0 の成功を成功と取り違えない (D-026)
- Bash ツールの既定のタイムアウトは 120 秒で、最大 600 秒。実入力のテストには、内部のウォッチドッグと、明示のタイムアウトを置く
- `.git`、`.cargo`、`.claude` は保護パスで、`allow` のルールでは書き込みを事前承認できない (D-021)
- `/goal` の評価者は、会話だけを見て判定する。サブエージェントや背景のシェルが動いているターンでは、評価が飛ばされる
- cargo の build script は、`cargo::rerun-if-changed` が 1 つも無いとパッケージ全体 (`.git` は含まない) を mtime で見る。ディレクトリを書くと中を走査する。存在しないパスを書くと毎回再実行する (via: Cargo Book「Build Scripts」の Change Detection と FAQ)。だから `build.rs` の引き金に git ディレクトリの `HEAD` と `index` を書かないと、コミットしただけでは版の印が「古い HEAD + dirty」のまま残る (D-069)
- この PC では `git commit` が `.git/index` も書き直す (via: `ls -l --time-style=full-iso .git/index .git/refs/heads/master` と `git log -1 --format=%ci` で、9810012 のコミット時刻 01:07:17 と両方の mtime が一致した。2026-10-16)。だから index を引き金にすれば、コミットの後の `cargo build --release` で印が更新される。`build.rs` の `git status` には `GIT_OPTIONAL_LOCKS=0` を付け、status 自身が index を書き直して自分の引き金を引かないようにする。dirty の原因のパスも引き金に出し、消えたパスは cargo が毎回再実行するのを利用して、固定の一覧に無い場所の dirty を git を介さずに消した次の build で印を clean に戻す
- Windows で `subprocess.run(timeout=...)` が時間切れで打つ kill は、子 (cargo.exe) 1 本の TerminateProcess で、孫 (rustc、テストの実行ファイル) は残る。木ごと止めるには `taskkill /T /F /PID <pid>` を打つ (scripts/verify.py の `kill_tree`。D-076)。確かめたのは cargo の孫ではなく python の孫で、`kill_tree` の本体を一時的に空にすると (根は `proc.kill()` が止める) 孫が残り、`test_run_all_reports_timeout_and_kills_grandchild` が落ちた (via: 実装のステップ 2 の対照と `python scripts/test_verify.py`、2026-10-22)。verify.py ごと外から止められたときは taskkill が打たれず、孫が残りうる (推定)。強制で止めた実入力のテストは後始末 (押したキーとボタンを離す) が走らないので、verify.py は ignored の時間切れで確かめるよう 1 行出す
